# ADR 0015: Application-Owned UUIDv7 Primary Keys And A Client-Suppliable `guid`

## Status

Accepted

Date: 2026-08-02

## Context

Two identifier questions had to be settled before first deployment, because both are effectively
irreversible once real data exists.

**Who generates the primary key?** Every table already used a UUID primary key, generated in Kotlin
with `uuidV7()` in the jOOQ adapters. That worked, but the ownership rule was a convention rather
than an enforced invariant, and 29 call sites elsewhere still used `UUID.randomUUID()` — version 4,
random. Random v4 primary keys scatter inserts across the whole B-tree instead of appending at the
right edge, which on a core-banking write path means avoidable page splits, index bloat, and cache
churn.

**How do external systems reference a row?** The platform is expected to grow into microservices.
A peer service, or a client integrating over the API, will want to create or update a record using
an identifier it chose, so that a retried or replayed write is recognisable as the same entity.
Letting clients choose the *primary key* is a different and worse proposition: it hands an external
party control over physical row placement, exposes internal enumeration, and makes the key's
uniqueness domain someone else's problem.

## Decision

Separate the two concerns into two columns.

**`id` — the primary key. Generated by us, never by clients.**

Every table that has an `id` is declared `id UUID PRIMARY KEY DEFAULT uuidv7()`. The database is
the default generator; the application reads the value back with
`.returning(TABLE.ID).fetchOne()?.id`.

Where an identifier is genuinely needed before the insert — an aggregate assembled in memory before
persistence, such as the `AuditEvent` domain object — application-side generation stays permitted,
but it **must** use `uuidV7()` from `com.finaxis.platform.common.id`. Both routes are the
application generating the identifier; only the layer differs, and the database is preferred.

`UUID.randomUUID()` is banned from production code, including for correlation ids and idempotency
keys, so that everything the platform generates is time-ordered.

Two tables have no `id` and are left alone: `api_idempotency_record` has the composite primary key
`(scope_organisation_id, idempotency_key)`, and `organisation_initial_administrator_bootstrap` uses
`organisation_id`. Neither gains a surrogate key.

**`guid` — the alternate key. Client-suppliable.**

Every application-owned table carries `guid UUID NOT NULL DEFAULT uuidv7()` with a unique
constraint. Because a column `DEFAULT` fires only when the column is omitted from the `INSERT`, one
declaration serves both cases: a client that supplies a `guid` has it stored verbatim, and one that
omits it gets a generated value.

**Scope limit:** no API surface accepts a client-supplied `guid` yet. The column, its uniqueness
guarantee, and its index exist now so that the migration is behind us; the write paths that accept
one arrive with the microservices split.

`uuidv7()` is a PostgreSQL 18 built-in (note the spelling — `uuidv7`, not `uuid7`), and the
platform pins `postgres:18.4` in both `compose.yaml` and `TestContainerImages`.

## Consequences

Primary keys are time-ordered, so inserts append to the right edge of every primary-key index
rather than scattering. The same now holds for `idempotency_key`, which is half of
`api_idempotency_record`'s primary key and previously came from `UUID.randomUUID()`.

Clients get a stable identifier they control for writes and updates, without any control over the
primary key, physical placement, or the internal identifier space.

Every table carries a second UUID column and a second unique index. That is real cost — roughly 16
bytes plus an index entry per row — accepted deliberately in exchange for a stable external key
that does not constrain the primary key. This duplication is worth being honest about: `id` is
already a UUID that a client could in principle have supplied, and `guid` exists because we
decided clients must *not* supply `id`.

Reading a generated key back with `RETURNING` means an insert that previously returned nothing now
returns a row, and the adapter must handle a null result. Every converted call site raises an
explicit error rather than silently returning a stale locally-generated value.

Anything that assumed it could compute a row's `id` before inserting must now either read it back
or use `guid` as the correlating key.

## Alternatives Considered

Let clients supply `id` directly and skip `guid` entirely:

- Rejected. It hands an external party control over primary-key placement and the uniqueness
  domain, and makes a malicious or buggy client able to influence index locality.

Keep application-side `uuidV7()` for primary keys and skip the database `DEFAULT`:

- Rejected as the default, though still permitted where an id is needed before insert. A database
  default makes the guarantee structural: a row inserted by a migration, a script, or a future
  service that forgets the convention still gets a correct, time-ordered key.

`gen_random_uuid()` as the column default:

- Rejected. It produces v4, which is exactly the index-locality problem being fixed.

Add `guid` only to the tables expected to be externally referenced:

- Rejected. Predicting which tables a future service will reference is guesswork, and adding the
  column later to a populated table is a far more expensive migration than adding it now while the
  database is empty.

## Verification

- `FoundationSchemaGuidTests` — all 36 application tables have a non-null `uuidv7()`-defaulted
  `guid` backed by a single-column unique index; generated values are distinct and time-ordered
- `FoundationSchemaConstraintTests` — a client-supplied duplicate `guid` is rejected
- `IdentifierGenerationRuleTests` — `UUID.randomUUID()` appears nowhere in production code, and no
  `*Request` DTO exposes a client-suppliable `id`
- Live verification against a fresh database: all 141 seeded `guid` values carry UUID version 7 and
  are distinct; a tenant created through the API received a database-generated v7 `id`
- ADR 0010, ADR 0014
